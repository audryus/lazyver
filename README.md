# lazyver

**lazyver** is a zero-effort version generator for lazy people. It derives your project's version straight from your git commit history — you just commit, and the version file is bumped, written and staged automatically before the commit is finalized.

## Why lazyver?

Because tagging releases manually is boring. With lazyver installed as a git hook, versioning becomes invisible:

- **Commit-driven bumps** — the version changes based on *what* you commit, not when.
- **Zero extra commands** — no `npm version`, no `git tag`, no ceremony. Just `git commit`.
- **Fast on huge repos** — the full history is read only once at initialization; afterwards only new commits are inspected (thanks to `lastHash`).
- **Self-contained** — uses your locally installed `git` binary, no library reimplementation of git.

## How it works

1. Run `lazyver semver` or `lazyver lazy` inside any git repository.
2. On the first run, lazyver reads the **whole commit history once**, computes the initial version and writes a control file `.lazyver.yaml` at the repository root:

   ```yaml
   version: v0.2.0
   major: 0
   minor: 2
   patch: 0
   kind: semver
   lastHash: 80dee7bf2fabab8e5aa6b34e75c611...
   pending: false
   last: 2025-01-15T09:19:47.01-03:00
   ```

3. It also installs a **`commit-msg` git hook** that calls lazyver back on every future commit.
4. From then on, each commit:
   - is classified by its message,
   - bumps the version,
   - and `.lazyver.yaml` is **staged automatically so it travels inside the same commit**.

> [!IMPORTANT]
> A repository cannot mix modes. If you need to switch from `semver` to `lazy` (or back), delete `.lazyver.yaml` and run again.

## Versioning modes

Pick one mode per repository:

### semver — conventional-commit driven

| Message pattern | Bump |
|---|---|
| `feat!: ...`, `fix(scope)!:` or footer `BREAKING CHANGE:` | major |
| `feat:`, `chore:`, `build:`, `docs:`, `ci:`, `test:`, `style:` | minor |
| `fix:`, `perf:`, `revert:`, `refactor:` | patch |
| anything else (merge commits, wip...) | none |

The type prefix is matched loosely, so `feature:` counts as `feat:` — lazy users are welcome.

### lazy — commit-count driven

The total number of commits is spread across the three version digits (hundreds → major, tens → minor, units → patch):

```text
  5 commits -> v0.0.5
 42 commits -> v0.4.2
339 commits -> v3.3.9
```

No rules, no thinking. Pure laziness.

## Usage

```bash
# Initialize/update with conventional-commit rules, printing the result
lazyver semver --path ./my-project -o

# Same, but using the lazy commit-count mode
lazyver lazy -o

# Operate on another repository
lazyver lazy --path ../other-repo

# Full help for a mode (rules + examples)
lazyver semver --help
```

Both commands:

- initialize the repository if `.lazyver.yaml` does not exist yet,
- otherwise update it incrementally from the stored hash,
- and (re)install the `commit-msg` hook.

There is also a hidden `lazyver hook <message-file>` subcommand — you should never call it yourself; the git hook does.

## CLI reference

| Flag | Description |
|---|---|
| `--path` | Path to the target repository (directory containing `.git`). Defaults to `.` |
| `-o`, `--output` | Print the resulting version (e.g. `v1.2.3`) to stdout |
| `-h`, `--help` | Show detailed help for any command |

## FAQ

**Why `commit-msg` instead of `pre-commit`?**
At `pre-commit` time the message doesn't exist yet, so there would be nothing to classify. `commit-msg` runs after the message is written but before the commit is finalized — exactly the right moment.

**What if I amend or rebase?**
Amending runs `commit-msg` again, which keeps the state consistent. History rewriting beyond that may require deleting `.lazyver.yaml` and re-initializing.

**Does `.lazyver.yaml` need to be committed?**
Yes — and lazyver stages it for you (`git add -f`), even if it matches a `.gitignore` rule.
